Introduction

Agentic and generative AI application architectures · Part 1

Suppose a support assistant answers a refund question correctly, then refunds the wrong order. Its answer was accurate; its action was wrong. The application accepted a generated identifier without checking that the customer could refund that order.

This series follows the decisions around that action: which evidence reaches the model, what its output can change, and how the application records the result. A better model may make fewer mistakes. The application still has to authorize the refund and record whether it happened.

The unit of design is the application

Berkeley’s compound-systems framing treats interacting models, retrieval, and tools as a design object. It is a useful starting point for reasoning beyond a single inference call. Berkeley AI Research: The Shift from Models to Compound AI Systems

Consider the following proposed reference architecture. The arrows indicate responsibility transfers, not an implementation tied to one framework.

flowchart LR
  U[User or event] --> A[Application API]
  A --> R[Run coordinator]
  R --> C[Context assembly]
  C --> M[Model gateway]
  M --> V[Output validation]
  V --> P[Policy and action boundary]
  P --> T[Tools and business services]
  T --> R
  D[Evidence and state stores] --> C
  R --> D
  R --> O[Telemetry and evaluation records]

The application API authenticates the request and identifies the task. The coordinator tracks progress and decides when work must stop. Context assembly supplies evidence and current state; the gateway provides inference access. Validation checks the result against a contract before the action boundary permits an operation. The business service enforces its own invariants throughout.

Start with these components as modules in one process. Separate boxes make responsibilities easier to discuss, but each service adds operational work. Extract one when requirements for scaling or isolation justify the boundary, or when independent ownership and release cycles require it.

Several kinds of correctness coexist

A generated answer can be readable yet unsupported. A tool call can satisfy its JSON schema yet target the wrong resource. An authorized operation can execute twice. A completed job can produce an artifact the user cannot retrieve.

Question Evidence required
Is the response supported? Claim-to-source relationships and source validity
Is the requested action allowed? Current identity, policy, resource, and action parameters
Did the external effect occur? Receipt, status query, or reconciled business state
Did the user’s task succeed? Task-specific postconditions, including prohibited changes
Can the service continue operating? Capacity, failure isolation, recovery, and cost indicators

Assign an owner to each check. The model can report confidence, but that report establishes none of the conditions in the table.

Generative applications do not require autonomous control

A document extractor may use one model call and deterministic validation. A knowledge assistant may retrieve, generate, and verify an answer through a fixed path. An agent lets model outputs influence the next operation in a loop. Multiple agents introduce additional coordination and resource decisions.

Anthropic distinguishes workflows and agents by who controls the next operation. Anthropic: Building effective agents A chat interface can front a deterministic workflow; a background process can be highly autonomous.

Make the business process explicit first. Let the model exercise judgment where the task requires interpretation, while application code enforces permissions around money and credentials. Apply the same discipline to destructive changes and persistent state.

The questions I’m working through

I’m writing these articles over time to work through the architecture of generative and agentic applications. I’ll draw on corporate engineering accounts and research papers, comparing the decisions behind them rather than presenting a single preferred stack.

Some questions are easier to examine through a complete application. I’ll use hypothetical knowledge assistants, support services, and research agents to connect the components. Voice and document-processing examples bring different timing and evidence constraints into the discussion.

The thread running through the articles is how a design holds up under its actual workload: where evidence comes from, who can authorize an action, and what survives a failure. Those questions should remain answerable when the model or framework changes.

Uber’s model gateway and LinkedIn’s agent-stack account provide two different industry entry points into shared application infrastructure. Neither should be copied without examining the surrounding requirements. Begin with a request trace

Before selecting a framework, trace one request from identity to final outcome. Mark every point where information changes representation, a decision gains authority, or an external effect becomes possible. For each transition, write down the owner, validation rule, timeout, and retained evidence.

For the refund assistant, this trace must show where a suggestion becomes permission to move money. Locate that transition before allowing the prototype to issue its first refund.
